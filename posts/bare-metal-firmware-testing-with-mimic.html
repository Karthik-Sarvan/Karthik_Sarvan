Building a Bare-Metal Firmware Testing Framework

Exploring how we constructed Mimic to emulate physical I2C and SPI sensors for testing control algorithms on the STM32 architecture without requiring the physical hardware.

When working on embedded systems, one of the biggest bottlenecks is often the hardware itself. You write the firmware, but to test it, you need the physical sensors, the actuators, and the exact PCB layout. If the hardware isn't ready, the firmware team is blocked.

The Problem with Physical Dependencies

At Aegion Dynamic Solutions, we faced this exact issue. We needed to test strict PID controllers and sensor fusion algorithms, but the custom PCB spins were delayed. We couldn't wait. We needed a way to trick the main MCU into thinking it was talking to real sensors over I2C and SPI.

"Hardware emulation is not just about mocking data; it's about mocking the physical timing and electrical behavior of a component."

Building Mimic

We built Mimic. It's a framework where a secondary, cheap STM32 board acts as a proxy. We wrote bare-metal C code to configure the STM32's peripherals in Slave Mode.

// Pseudocode for configuring I2C Slave
I2C_Slave_Init(I2C1, 0x68); // Emulate MPU6050 address
while(1) {
    if (I2C_Data_Requested()) {
        I2C_Transmit(mock_sensor_data);
    }
}

By connecting this proxy board to our main MCU, we could feed it perfectly crafted edge-case data (like simulated sensor drift, extreme temperatures, or dropped packets) that are extremely difficult to reliably reproduce in the physical world.

Results

  • Reduced firmware testing bottlenecks by 60%.
  • Caught 3 edge-case race conditions in the PID loop before hardware even arrived.
  • Created a reusable Python bridge to inject mock data into the proxy board in real-time from a PC.

Writing bare-metal firmware requires patience, but when you build tools to accelerate your own workflow, the return on investment is massive.

What I'd do differently

The first version of Mimic hard-coded every device profile. The second version moved profiles into a plain data table that the Python bridge uploads at runtime, which meant adding a new emulated part went from a firmware rebuild to a config change. If you are starting a similar framework, make the device model data before you make it code — it is the difference between a demo and a tool your team will actually keep using.
