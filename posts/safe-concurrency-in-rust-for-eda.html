Safe Concurrency in Rust for EDA

How Rust's ownership model allowed us to parse massive component datasheets concurrently without data races in the Pratibim core engine.

An EDA co-pilot lives or dies on how fast it can turn a messy, human-written datasheet into structured data. A single manufacturer can publish thousands of parts, each with a different table layout, a different unit convention and a different idea of what "typical" means. Ingesting that corpus serially was the first wall we hit at Pratibim.

Why the naive version breaks

The obvious design is a shared part index: one big map from part number to record, with worker threads reading PDFs and writing into it. In C++ or Java that design compiles, ships, and then corrupts itself under load — two workers rehash the same bucket, one write is lost, and the bug shows up three weeks later as a component with the wrong package footprint.

Rust refuses to compile that program. A Mutex<HashMap> would work, but the borrow checker forced us to ask a better question first: do these workers actually need to share anything?

"Fearless concurrency is not the absence of bugs. It is the compiler telling you, at 2 a.m., that your design was wrong before production tells you at 2 p.m."

Send and Sync as a design review

Send means a value can be moved to another thread; Sync means it can be shared by reference across threads. Those two marker traits are auto-derived, which means they act like a free, always-on design review of every type in the codebase.

When our parser struct stopped being Send, the compiler was pointing at something real: we had stuffed a Rc<UnitTable> into it. Rc has a non-atomic reference count, so it is deliberately not thread-safe. Switching to Arc made it compile — but the better fix was to stop sharing the table at all and let each worker own a reference to an immutable, pre-built table behind a single Arc created once at startup.

Map, then reduce — never share-and-mutate

The final architecture is embarrassingly parallel, which is exactly what you want:

use rayon::prelude::*;

// Each worker owns its inputs and returns an owned value.
// Nothing is mutated in place, so no lock is ever taken.
let parts: Vec<Part> = datasheets
    .par_iter()                       // work-stealing thread pool
    .filter_map(|doc| parse(doc).ok())
    .collect();                       // reduce into one owned Vec

// The index is built once, from owned data, then frozen.
let index: HashMap<PartNumber, Part> =
    parts.into_iter().map(|p| (p.pn.clone(), p)).collect();

Because par_iter hands each worker a &Datasheet and takes back an owned Part, there is no shared mutable state anywhere in the hot path. rayon work-steals across cores, so a 400-page datasheet does not stall the whole batch.

The two places we did need atomics

  • Progress reporting. A single AtomicUsize counter, incremented with Relaxed ordering — we only need eventual accuracy for a progress bar, not ordering guarantees.
  • Dedupe on part number. A Mutex<HashSet<PartNumber>> held for microseconds. Contention was measurable, so we sharded it by hash prefix and contention dropped to noise.

What it bought us

  • Corpus ingestion went from roughly linear-in-documents to bound by core count, with no locking in the parse path.
  • Zero data races found in production — not because we were careful, but because the type system made the buggy version unrepresentable.
  • Parser crashes became isolated: a panic in one worker takes down one task, and Result propagation means a malformed datasheet is logged and skipped instead of poisoning the index.

The lesson generalises well beyond EDA. When a language makes you prove that your threads do not share mutable state, you end up writing the architecture you should have written anyway — and it happens to be the fast one.
